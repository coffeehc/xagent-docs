这次案例里最值得写的，不是“AI 会搭建抓包环境”。

真正让我意外的是，驱动整个过程的底层模型只是 **Qwen3.8-27B AWQ INT4**。一个 27B、4bit 量化的模型，在 xAgent 上完成了服务器与 Android 手机的环境探测、工具部署、设备联调、代理链路打通和真实流量验证。

这不是一道提前准备好的演示题。测试服务器和手机都是真实设备，过程中也遇到了 Android 用户证书信任范围、原生 App TLS 握手失败和无 Root 设备能力受限等实际问题。

## 我只做了两件事

我给 xAgent 一台测试服务器和一部 OPPO 手机，目标是搭建一套可以分析手机网络流量的测试环境。

整个过程中，我实际操作的只有两件事：

1. 打开手机的 WLAN 调试。
2. 把测试服务器和手机接入同一个网络。

剩下的工作都通过与 xAgent 的自然语言交互推进。我没有手工登录服务器安装工具，也没有自己拼 ADB、代理或 Frida 命令。

这里讨论的是我拥有控制权的测试服务器和测试设备。抓包、调试和安全分析都应该只在明确授权的环境中进行。

## xAgent 实际完成了什么

xAgent 先探测手机型号、Android 版本、无线 ADB 地址和配对状态，然后在服务器和手机之间建立连接。连接验证完成后，它继续准备整条工具链：

- 在服务器上创建独立环境并部署 `mitmproxy 11.0.2`。
- 在服务器和 Android 设备上分别准备 `Frida 17.17.0`。
- 为设备准备网络与代理测试所需的辅助工具。
- 通过无线 ADB、反向端口映射、Android 全局代理和服务器网络规则打通链路。
- 启动持续日志，并实际验证设备流量能够到达代理服务器。
- 保存后续会话可以复用的设备连接信息。

![xAgent 完成 Android 测试设备探测、mitmproxy 与 Frida 部署以及代理链路验证](/img/blog/xagent-27b-int4-android-packet-capture/environment-ready-zh.webp)

*第一阶段完成时，xAgent 已经列出工具版本、部署位置、代理链路、验证结果和无 Root 环境的限制。*

如果任务停在这里，它仍然可能只是一次“命令都执行成功”的演示。进程启动、端口监听和工具返回成功，并不能证明手机的真实请求已经被正确记录和解密。

## 真正重要的是后续验证

xAgent 随后继续读取 mitmproxy 的真实日志，验证不同类型的手机流量。

结果不是简单的“成功”或“失败”：

- 手机浏览器主页的 HTTPS 请求返回 `200 OK`，内容可以解密，说明用户 CA 已被浏览器或 WebView 信任。
- 浏览器自身的部分后台组件返回 `certificate unknown`，说明它们没有采用同一条用户证书信任链。
- 其他原生 App 的 HTTPS 连接只能看到 TLS 握手，无法直接看到请求内容。

![xAgent 根据 mitmproxy 真实日志区分浏览器、WebView 与原生 App 的证书信任结果](/img/blog/xagent-27b-int4-android-packet-capture/traffic-validation-zh.webp)

*第二阶段没有把受平台限制的流量误报为配置失败，而是根据真实日志划分了当前抓包能力。*

xAgent 最终把结果分成三档：普通 HTTP 与信任用户证书的浏览器、WebView 流量可以看到明文；不信任用户证书的原生 App 只能看到连接与 TLS 握手；需要系统级证书、全量镜像或更深进程调试的场景，则需要 Root 或针对目标 App 单独分析。

它还补强了代理侧的上游证书处理和持续日志配置。也就是说，任务没有在“工具装好了”时结束，而是在真实请求给出可解释的结果后才收口。

## Android 的边界也是结果的一部分

这台手机没有 Root。Android 7 及之后，应用默认不会自动信任用户安装的 CA；应用是否接受用户证书，取决于它自己的网络安全配置、使用的网络栈以及是否启用了证书固定等机制。

因此，同一张证书在浏览器或部分 WebView 中生效，不代表所有原生 App 都能解密。无 Root 环境下看不到某些 HTTPS 明文，不是工具链部署失败，也不应该被包装成“已经完全抓通”。

这个判断很重要。Agent 真正可用的标志，不是永远给出成功结论，而是能根据证据区分：哪里已经完成，哪里受平台机制限制，下一步需要什么条件。

## 为什么这更像一个 27B INT4 的故事

如果底层使用的是规模最大的闭源模型，这个结果依然有价值，但不会像现在这样有冲击力。

27B、4bit 量化意味着模型规模和推理成本都相对可控。它并没有因为参数量较小，就只能回答“如何安装 mitmproxy”或生成一段操作指南。在 xAgent 中，它把一次开放式目标推进成了连续的工程过程：

- **有行动环境**：模型可以使用被授权的服务器、终端和设备连接，而不是只输出文字。
- **有状态连续性**：设备信息、已经完成的步骤和当前限制可以进入后续判断，不必每轮重新开始。
- **有执行反馈**：命令结果、进程状态和真实代理日志会回到上下文，模型可以据此修正下一步。
- **有目标约束**：任务目标不是“调用一次工具”，而是建立一条能被验证的抓包链路。
- **有边界意识**：权限、设备状态和 Android 平台机制决定哪些动作成立，模型不能用一段看似合理的回答替代事实。

抓包验证结束后，我继续让 xAgent 研究这台设备的 Root 可行性。它先确认芯片、Bootloader 状态、系统版本与区域，再区分官方解锁和其他技术路线，并明确指出：后续至少需要一次 USB 物理接入，解锁可能清除全部数据、影响保修，也存在设备变砖风险。它没有把无法远程完成的步骤包装成“可以自动搞定”。

![xAgent 在长会话中继续评估 Android 设备 Root 路线，并明确物理操作与风险边界](/img/blog/xagent-27b-int4-android-packet-capture/long-session-root-assessment-zh.webp)

*页面顶部显示当前上下文为 `123k / 160k tokens`，该会话累计处理约 `35.97M tokens`，缓存命中约 `23.32M tokens`，并完成 `612` 次工具调用。这里是整个会话的累计统计，不是单次抓包任务的独立消耗。*

这组数据的价值，不是说明 token 用得越多越好，而是证明这不是几轮对话碰巧成功。经过大量工具反馈和上下文推进后，27B INT4 模型仍然能够继续读取当前设备事实、识别缺少的物理条件，并给出与风险边界一致的下一步判断。

这正是 Agent Harness 的价值。模型负责理解、推理和选择动作；xAgent 负责把工具、状态、权限、长期任务和结果反馈组织成一条可以持续推进的执行链。

当然，一次案例不是通用 benchmark，也不能证明所有 27B 模型都能稳定完成所有复杂任务。结果仍然取决于模型本身、上下文长度、工具调用质量、运行环境、权限边界和目标复杂度。但这个案例至少给出了一个真实证据：在合适的 Agent 系统里，量化模型能够完成远超普通聊天问答的工程任务。

## 从产品建设转向真实案例

xAgent 的主体现在已经基本稳定。接下来更重要的，不是继续堆叠抽象概念或功能清单，而是把它放进更多真实环境，看看它究竟能完成什么、会在哪里失败、又如何根据结果继续推进。

这篇文章也会是“xAgent 实战案例”系列的开始。后续案例仍会保留完整任务背景、用户实际做了什么、xAgent 执行了什么、最后如何验证，以及过程中遇到的真实边界。

真正值得关注的，不是 xAgent 又会调用一种工具，而是：

> 当一个 27B、AWQ INT4 量化模型进入具备工具、状态和验证闭环的 xAgent，它不再只是一个会回答问题的模型，而开始成为能够在真实环境中完成任务的工程 Agent。
