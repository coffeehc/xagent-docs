# xAgent 文档站 SEO / GEO 执行协议

- 状态：生效
- 版本：2.0
- 生效日期：2026-08-01
- 适用范围：xAgent 文档站的中文与英文首页、Docs、Blog、Insights、Changelog、搜索入口和机器可读入口
- 维护位置：`.codex/seo/seo-geo-protocol.md`

## 1. 协议定位

本协议是 xAgent 文档站 SEO 与 GEO 工作的唯一规范来源。它约束关键词研究、内容选题、写作、翻译、技术实现、发布、外部分发和发布后复盘。

其他文件的职责如下：

| 文件 | 职责 | 是否作为规则来源 |
| --- | --- | --- |
| `seo-geo-protocol.md` | 稳定执行规则和质量门槛 | 是 |
| `keyword-pool.md` | 关键词、意图、落地页与状态的当前值 | 否 |
| 日期命名的研究记录 | 保存当期 SERP、工具数据、样本和判断 | 否 |
| `SEO_STRATEGY.local.md` | 本地阶段性策略、优先级和待办 | 否 |

出现冲突时，以本协议为准；新的实测结果不能直接成为长期规则，必须先更新本协议并记录依据。

## 2. 规范用语

- **必须**：发布或合并前必须满足；不能满足时必须停止并记录阻塞原因。
- **应当**：默认执行；跳过时必须有与当前页面相关的明确理由。
- **可以**：根据搜索意图、页面类型和证据决定，不作为固定模板。
- **禁止**：不得执行，工具建议或竞品做法不能覆盖该限制。

SEO 指页面能够被搜索引擎发现、收录、理解，并准确承接用户搜索意图。GEO 指页面能够被生成式搜索或问答系统准确理解、检索、归纳和引用。GEO 不替代 SEO，也不承诺获得 AI Overview、Featured Snippet 或模型引用。

### 2.1 规则层级

所有检查项必须标明来源和强度，禁止把内部质量门槛写成 Google 排名要求：

| 层级 | 含义 | 处理方式 |
| --- | --- | --- |
| Google 技术最低门槛 | Googlebot 未被阻止、页面返回成功状态、正文可编入索引 | 不满足即阻塞发布 |
| Google 政策 | Search Essentials 与垃圾内容政策 | 违反即阻塞发布 |
| Google 强烈建议 | 有用内容、可抓取链接、规范 URL、移动端一致性、页面体验等 | 默认执行；例外必须说明 |
| 条件性增强 | Article、Breadcrumb、图片、视频、商家或垂直搜索能力 | 仅在页面类型和可见正文真实匹配时使用 |
| xAgent 内部门槛 | 唯一 H1、唯一 description、双语结构校验、全站构建爬取等 | 作为仓库发布门槛，不宣称是排名因素 |

第三方工具、模型回答、SERP 样本和经验文章只能提出待验证假设。与官方文档冲突时，以 Google 当前官方文档和真实产品事实为准。

## 3. 总原则

1. **用户任务优先。** 页面必须让目标读者在当前页面完成主要任务，而不是只覆盖关键词。
2. **产品事实优先。** 产品行为必须来自当前代码、当前文档、当前版本、真实截图、配置、测试或任务结果。
3. **第一手证据优先。** 实际部署、执行链、失败复盘、测试结果和边界说明优先于通用观点。
4. **一个意图对应一个权威页。** 已有页面能够承接时优化原页，禁止创建近义页面参与内部竞争。
5. **正文优先于包装。** 元数据、Schema、`llms.txt` 和关键词工具不能弥补空泛、重复或不可验证的正文。
6. **可验证而非可营销。** 不承诺排名、流量、收入、AI 引用、完全自治、绝对安全或其他无法持续证明的结果。
7. **SEO 与 GEO 共用质量基础。** 可抓取正文、明确结论、稳定术语、来源、版本、内部链接和页面体验同时服务搜索引擎、生成式系统与真实读者。
8. **Google AI 搜索没有单独捷径。** Google AI Overview 和 AI Mode 仍以搜索索引、核心排名与质量系统为基础，不需要特殊 GEO Schema、AI 文本文件或专门改写文风。
9. **满足规范不等于保证展示。** 抓取、索引、富结果、AI 引用、站点链接和标题摘要都由系统决定，任何检查通过都不能写成结果承诺。

### 3.1 强制执行顺序

每次全站 SEO/GEO 检查或较大优化必须按以下顺序进行，禁止先改页面再倒推规则：

1. 复核本协议及与本次页面类型相关的 Google Search Central 当前官方章节；
2. 建立源码、路由、语言、内容类型、sitemap 和索引状态清单；
3. 完整构建站点，并对所有生成 HTML 做技术爬取；
4. 逐页检查搜索意图、内容责任、第一手证据、重复内容、语言质量和下一步入口；
5. 记录问题、规则依据、影响 URL、误报和不修改理由；
6. 只修改已确认问题，不为消灭工具提示扩大范围；
7. 重新构建、全站复测，并保存覆盖数量与验证结果。

针对单篇新内容可以缩小清单范围，但仍必须先确认规则和页面责任，再写作和修改。

## 4. 内容类型与责任

### 4.1 Docs

Docs 负责当前产品是什么、如何安装、如何配置、如何使用，以及准确的协议、状态和安全边界。

- 必须保持操作步骤、配置、菜单、版本和产品行为准确。
- 应当直接解决任务，不写成行业观点或营销文章。
- 技术实现、协议和 Runtime 边界必须放在“技术参考”类信息架构下，不与普通用户功能指南混放。

### 4.2 Blog

Blog 负责真实场景、实施过程、操作教程、故障复盘、版本背景和结果验证。

- 必须包含实际过程、产物或可验证结果。
- 禁止仅改写 Docs。
- 必须链接到对应 Docs；高价值 Blog 发布后，相关 Docs 应当增加“相关实践”入口。

### 4.3 Insights

Insights 负责有事实来源和独立判断的行业分析、方案比较与决策框架。

- 必须区分事实、观察、推断和建议。
- 必须给出适用条件、限制和决策依据。
- 禁止发布泛化 AI 新闻摘要或没有独立价值的搜索结果汇编。

### 4.4 Changelog

Changelog 是版本日期、变更、兼容性和升级事项的稳定事实源。

- 小修复只进入 Changelog。
- 重要功能版本可以同时发布 Blog/Release Notes，补充背景、场景、截图、兼容影响和升级步骤。
- Changelog 与对应文章必须互相链接；Blog 不能替代 Changelog 的事实源责任。

### 4.5 首页与导航页

- 首页必须清楚表达产品、目标用户、主要能力、边界和下一步入口。
- 列表页必须有可见且唯一的 H1；空列表页应当 `noindex,follow`，不得作为可索引占位页。
- 没有独立搜索意图、只有少量重复摘要的标签、作者和归档聚合页应当保留导航功能但使用 `noindex,follow`，并从 sitemap 排除；只有能提供独立价值时才恢复索引。
- 导航名称必须符合读者心智，不能为了关键词把技术页面放进错误栏目。

## 5. 关键词与选题协议

### 5.1 候选词池

所有候选词必须维护在 `.codex/seo/keyword-pool.md`。每行只记录一个搜索词，并记录：

- 语言；
- 主题集群；
- 搜索意图；
- 目标读者；
- 产品事实依据；
- 对应落地页；
- 数据来源与日期；
- 当前状态。

状态只允许：`已选题`、`优化现有页`、`候选`、`观察`、`排除`。

候选来源按以下顺序使用：

1. Search Console 已有展示、低点击或排名仍有提升空间的查询；
2. Issues、Discussions、客服、社区和真实用户反复提出的问题；
3. 已发布功能、版本变化、真实部署和故障过程中出现的问题；
4. Google Autocomplete、Google Trends、Ahrefs、Keyword Planner 等研究工具；
5. 与当前产品能力直接相关的内容缺口。

由 Gemini、ChatGPT 或其他生成式系统列出的“常见问题”“回答模糊的问题”只能作为候选线索。进入关键词池前，必须再用 Search Console、真实 SERP、Issues、Discussions、客服记录、社区讨论或用户访谈验证需求，并确认 xAgent 有可公开的第一手答案。

禁止仅因热度高就收录与 xAgent 当前能力无关的泛化 AI 词。

### 5.2 选题

- 每篇页面必须只有一个主要搜索意图。
- 每篇页面应当选择一个主词和 2 至 4 个辅助词。
- 主词、辅助词和落地页必须在写作前写入关键词池。
- 已有权威页能够承接相同意图时，必须标为“优化现有页”，不得新建同义页面。
- 选题优先级依次为：真实用户问题、产品独特实现、已有展示低点击、版本变化解释、经验证的新需求。
- 泛词、评测词、价格词或竞争产品词只有在搜索意图、产品事实和证据均匹配时才可进入选题。

### 5.3 数据边界

- 没有实时 SERP 或搜索量时，必须标记为“策略候选”或“未验证”，不得表述为测量结果。
- Ahrefs KD、搜索量、DA、DR 或商业价值只能引用工具实际返回的数据。
- KD 只用于初筛，不能替代当前 SERP、域名类型、内容质量、产品匹配和真实竞争判断。
- Google Trends 数值只表示指定时间、地区和搜索类型下的相对热度，不得写成绝对搜索量。
- Search Console 的小样本、过滤视图和不完整聚合只能作为方向信号，不得过度解释趋势。
- 禁止伪造、反推或用页面外链数量冒充 DA、DR、KD、搜索量。

## 6. SERP 与搜索意图研究协议

每个新选题发布前必须检查当前目标查询的搜索结果。研究记录必须包含查询、日期、地区或语言、样本页面和数据限制。

### 6.1 必查内容

1. 用户需要定义、比较、教程、排障、评测、购买还是导航结果；
2. 结果页是否有 AI Overview、Featured Snippet、视频、图片、People Also Ask 或其他特殊形态；
3. 前列页面如何直接回答问题；
4. 常见章节、决策维度、使用场景和遗漏问题；
5. 可引用的第一手或权威来源；
6. xAgent 能提供的独特事实、案例、限制和下一步入口。

### 6.2 可统计维度

可以统计前十页面的字数、标题层级、H2/H3、表格、FAQ、外链、图片和视频，但这些指标只用于理解结果页，不是排名规则，也不是写作配额。

- 禁止为了接近竞品中位数字数而扩写。
- 对比表只在关系确实更容易比较时使用。
- FAQ 只回答真实高频问题，不为富结果凑数量。
- 图片、视频和代码只在帮助用户核验或完成任务时使用。
- 当前结果页没有 Featured Snippet 时，不得假设存在“零号位”答案模板。

Codex 可以替代 Perplexity 完成检索、页面结构审计、搜索意图归纳和候选筛选。Codex 不能替代 Ahrefs、Keyword Planner、Search Console 等工具的专有或站点私有数据。

### 6.3 生成式搜索基线

Google AI Features、Gemini Apps、ChatGPT Search 和 ChatGPT Shopping Research 是不同系统，必须分别建立基线，禁止把一个系统的观察外推为另一个系统的规则。

基线记录必须包含：

- 用户原始问题及其语言、地区和意图；
- 使用的产品模式、日期，以及会影响结果的 Memory、Custom Instructions 或其他上下文；
- 答案提到的产品、页面和实际显示的来源 URL；
- 引用是否准确、是否仍符合当前版本、遗漏了哪些关键事实；
- 同一问题复测时结果是否变化。

Gemini Apps 并非每次回答都提供来源；显示的来源或相关链接也不能证明页面被选择的内部原因。必须打开来源核对原文、时效和声明边界，禁止让 Gemini 自己解释“为什么推荐”并把回答当作检索或推荐机制证据。

单次回答只能作为观察样本，不能称为“排名”或“推荐池位置”。应当用一组稳定问题持续复测，但不设固定回答数量或固定入选数量。回答中提到的品牌只作为对比样本，不能直接定义为完整竞品集合。竞品页面的共同结构只能用于提出内容缺口假设，不能解释为生成式系统的准入门槛，更不能要求按竞品段落顺序仿写。

## 7. 内容简报协议

进入写作前必须形成内容简报，至少包含：

- 目标读者与要完成的任务；
- 主搜索意图、主词和辅助词；
- 页面类型与落地路径；
- 页面承诺和读者完成后的结果；
- 标题、slug、description 和首段直接答案草稿；
- H2/H3 结构；
- 第一手案例、证据和待验证声明；
- 内部链接、外部来源和下一步入口；
- 适用版本、限制、安全边界和发布阻塞项。

建议 slug 必须小写、短、稳定并使用连字符。元数据是准确包装，不是排名承诺。

## 8. 写作与证据协议

### 8.1 直接答案

- 标题、H1、首段和 description 必须自然表达主要问题，不堆叠关键词。
- 首屏必须直接回答主要搜索意图，再展开背景、步骤和证据。
- 第一段应当短而完整；“直接答案 + 详细展开 + 数据或案例支撑”可以作为组织方法，但不是固定模板。
- Featured Snippet 或 AI Overview 只作为可能的展示结果，不作为内容真实性或质量判断标准。
- 不设固定字数、段落长度、H2/H3 数量或所谓“理想内容长度”；篇幅由读者任务决定。

### 8.2 正文结构

每篇内容必须包含与意图匹配的以下信息：

1. 适用场景与不适用场景；
2. 真实操作步骤，或完整的“输入 - 执行 - 输出”案例；
3. 当前版本的截图、配置、测试数据、任务结果或文档证据；
4. 限制、失败方式、安全边界和人工确认点；
5. 明确的下一步入口。

文章应当使用短段落、语义明确的标题和可扫描结构。列表、表格、代码和图片必须帮助理解，不能承载无关装饰或关键词重复。

### 8.3 FAQ

- 有真实常见问题时，可以提供简洁 FAQ；数量以完整解决问题为准，不设 3 至 5 个或 5 至 8 个等固定指标。
- 没有足够真实问题时，不设置 FAQ，并在研究记录中说明。
- FAQ 的目标是完成用户任务，不是获得 FAQ 富结果。
- FAQ 答案必须与正文和当前产品事实一致。

### 8.4 来源与声明

- 产品行为必须引用当前文档、发布记录、真实截图、配置、测试或任务产物。
- 外部事实必须优先引用官方文档、原始研究、标准、作者原文或其他第一手来源。
- 引用必须靠近对应声明，不能只在文末堆放链接。
- 经验、解释、推断和建议必须明确区分。
- 未验证声明必须标记为待验证，不得补写虚构来源、数据、案例、引语或第一手经验。
- 具体数字和实测结果必须来自真实记录，并说明对象、版本、环境、方法、时间和限制；生成式工具不得自行补齐数字。
- 禁止把未发布功能、推测性路线图或未来计划写成当前能力。
- 禁止使用“最佳”“完全免费”“绝对私有”“保证排名”等无法长期证明的标题或结论。
- 页面应当在有助于信任判断时说明谁创作、如何验证以及为何发布；AI 或自动化参与达到读者合理关心的程度时，应当准确披露其用途和人工核验方式。

### 8.5 内部链接

每篇新文章至少必须链接：

1. 一个核心产品或概念页；
2. 一个实际操作或功能文档页；
3. 一个安全、部署或相关主题页。

链接文本必须描述目标内容，禁止使用没有语义的重复“点击这里”。所有锚点必须在构建后验证存在。

## 9. 中英文协议

- 中文与英文必须保持同一产品事实、版本、限制、安全边界和发布时间关系。
- 两种语言必须按各自用户的搜索表达、案例背景和阅读习惯独立组织，禁止机械逐句翻译。
- 只有两种语言都存在明确需求且能够维持同等事实质量时，才应同步发布。
- 缺少真实翻译时，英文回退到中文源页面必须 `noindex,follow`，不得让重复语言内容参与索引。
- 更新一侧的产品事实时，必须检查另一侧是否需要同步；有意不同步时必须记录原因。
- 不同语言必须使用独立稳定 URL、可见语言切换入口和完整互指的 hreflang；不得按推测语言自动重定向并阻止用户访问其他语言。
- Google 主要根据可见正文判断语言；`lang` 属性、URL 或 hreflang 不能弥补英文 URL 中的中文正文。
- 同一语言存在重复 URL 时，先确定该语言 canonical，再让 hreflang 指向该 canonical。

## 10. GEO 协议

Google 搜索范围内的 GEO 属于 SEO，不建立第二套页面写法。页面只要符合搜索技术要求、可显示摘要并已编入索引，就具备进入 Google AI 功能辅助链接的技术资格；不存在额外技术要求，也不保证实际展示。

### 10.1 可理解与可引用

- 重要结论必须存在于服务器生成或静态生成的可抓取正文中，不能只存在于图片、视频、Canvas 或点击后脚本状态中。
- 每个重要章节应当围绕一个明确问题，首段给出可独立理解的结论，再提供条件、步骤、证据和例外。
- 术语、产品名、功能名、协议名和状态名必须稳定一致；首次出现时应当定义，容易混淆的概念必须直接区分。
- 数据、版本、实验和行为声明必须带适用时间或版本，避免生成式系统把历史行为概括为当前事实。
- 表格表头、列表项和代码上下文必须完整，截取单个段落后仍应能判断对象和适用条件。

### 10.2 来源与实体一致性

- xAgent 的名称、定位、站点 URL、文档 URL 和产品描述必须在首页、Docs、Blog、Insights、Changelog、结构化数据和 `llms.txt` 中保持一致。
- 原始来源必须优先于二次摘要；无法验证的聚合页不能支撑关键结论。
- 页面作者、发布日期、更新时间、适用版本和来源必须与可见内容一致。
- 产品页面应当通过明确内部链接形成主题关系，不依赖模型自行推断页面归属。

### 10.3 机器可读入口

- Google 搜索及其 AI 功能不使用 `llms.txt` 提升抓取、排名或引用。`static/llms.txt` 只作为其他明确消费者的核心内容导航和辅助入口，不是正文镜像，也不是 Google 优化项。
- 新增、删除或重命名核心公开页面时，必须检查 `llms.txt` 链接和描述。
- 禁止新增没有官方支持、没有真实消费者或与页面正文不一致的 AI 专用 Schema、隐藏文本或关键词块。
- 结构化数据、sitemap 和 `llms.txt` 必须指向同一组真实、公开、规范化页面。

### 10.4 ChatGPT 可发现性

- 需要进入 ChatGPT Search 摘要、引用和链接的公开页面，不得在 `robots.txt` 中屏蔽 `OAI-SearchBot`。
- `OAI-SearchBot` 控制搜索发现，`GPTBot` 控制潜在训练用途；两者职责不同，不得把训练授权当作搜索收录条件。
- 允许抓取只提供被发现的资格，不保证页面被引用、推荐或获得固定位置。
- ChatGPT 转介链接通常包含 `utm_source=chatgpt.com`，应当通过站点分析记录转介访问、落地页和后续转化。
- 电商页面应当优先保证商品名称、规格、价格、库存、商家身份和来源一致；存在真实电商业务时，可以评估 OpenAI 支持的商品 Feed、ACP 或平台目录接入。xAgent 当前不是商品目录，不为 GEO 虚构电商 Feed。

## 11. 技术 SEO 协议

### 11.1 URL、索引与状态码

- 可索引页面必须允许 Googlebot 抓取、返回 HTTP 200，并提供可编入索引的正文；这是 Google 技术最低门槛。
- 公开页面必须使用稳定、可读、规范化 URL；slug 使用小写和连字符，避免片段 URL、无意义参数及同内容多套 URL。
- 删除或迁移页面必须根据是否有等价替代内容选择 301 或 404/410，禁止全部重定向到首页。
- 永久迁移优先使用服务端 301/308；302/303/307 只用于临时迁移。
- sitemap 只能包含规范、可索引、返回成功状态的 URL。
- 搜索结果页、空列表、未翻译回退页和不应参与搜索的功能页应当使用 `noindex,follow`，并从 sitemap 排除。
- 404 页面和任意不存在路径必须返回 404/410；若托管平台允许 404 文档本身以 200 访问，该文档必须显式 `noindex,follow`，避免软 404 被索引。
- `robots.txt` 不得屏蔽公开正文所需的页面、样式或关键资源。
- `robots.txt` 用于管理抓取，不用于移除索引；需要 `noindex` 的页面必须仍允许抓取，使搜索引擎能够读取该指令。
- 重要内容必须在服务端生成或静态生成 HTML 中提供。JavaScript 不能阻止正文、title、description、canonical、链接和结构化数据被渲染；移动端不得要求交互后才加载主要正文。

### 11.2 Canonical 与 hreflang

- 每个可索引页面必须有与实际公开 URL 一致的 canonical。
- 存在中英文对应页时，必须生成正确、互相对应的 hreflang。
- 不存在高质量翻译时，不得创建只为占位的可索引语言页面。
- canonical、hreflang、站内链接和 sitemap 中的 URL 必须一致。
- canonical 应当自引用；站内链接必须直接指向 canonical URL。重定向和 `rel=canonical` 是强信号，sitemap 是较弱的规范化信号。

### 11.3 Sitemap 与更新时间

- 中文与英文 sitemap 必须在 `robots.txt` 中声明，并在 Search Console 中提交和监控。
- sitemap `lastmod` 只能因正文、结构化数据、重要链接或其他实质变化更新。
- 禁止为了制造新鲜度批量刷新日期。
- sitemap 使用绝对 canonical URL；`priority` 与 `changefreq` 不作为 Google 调度信号。`lastmod` 只有准确反映实质更新时才保留。
- 新增、更新或删除 URL 后，可以使用 IndexNow 通知支持该协议的搜索引擎，但它不能替代 sitemap 和正常抓取。

### 11.4 页面元素

- 作为 xAgent 内部门槛，每个可索引页面必须只有一个清晰、可见的 H1。
- 作为 xAgent 内部门槛，每个可索引页面的 `title` 和 description 必须准确、具体且保持唯一；它们应当与 H1 一致但不机械重复。
- description 必须用一句自然语言说明页面价值，不使用诱导点击文案。
- Google 可能根据查询改写标题和摘要；title 与 description 只提供准确候选，不保证按原文显示。标题和主要可见标题必须使用页面主体语言。
- H2/H3 必须表达信息层级，禁止为了关键词数量制造空标题。
- 页面内锚点、导航、面包屑和内部链接必须在构建产物中有效。
- 重要页面至少必须有一个可抓取的内部 `<a href>` 链接；锚文本必须简洁、具体并说明目标内容。外部链接可用于支撑来源，但不得购买或操纵。
- 禁止使用 `meta keywords`。
- 首页应当使用一致的站点名称，并可用与可见品牌一致的 `WebSite` 结构化数据表达站点名称偏好；网站图标必须可抓取、方形、稳定且至少 8x8，建议大于 48x48。

### 11.5 结构化数据

- Schema 必须与页面可见内容、页面类型和当前事实一致。
- Docs 可使用与实际类型匹配的 `TechArticle`、`WebPage`、`ContactPage` 或 `CollectionPage`。
- Blog 或 Insights 发布文章时，必须验证并补齐适合的 `Article` 或 `BlogPosting`、作者、发布日期和更新时间。
- 可以评估 `BreadcrumbList`，但层级必须与可见导航一致。
- 禁止创建页面上不存在的作者、评价、价格、组织、FAQ 或产品声明。
- 结构化数据不是生成式搜索的特殊准入条件，也没有专门的 GEO Schema。
- 结构化数据只提供富结果资格和理解线索，不是排名保证；JSON-LD 为推荐实现方式，但所有字段必须可见、最新、相关且可验证。
- 普通产品、文档和文章页面不得为了“更容易被 AI 引用”批量添加 `FAQPage`。Google 的 FAQ 富结果通常只面向符合资格的权威政府和医疗网站；可见 FAQ 可以存在，但 Schema 必须服从实际页面类型和当前官方支持范围。

### 11.6 图片、视频与页面体验

- 重要信息不能只存在于媒体中；图片和视频必须有等价正文上下文。
- 信息图片必须提供准确 alt，装饰图片使用空 alt。
- 截图必须对应当前语言、当前版本和正文描述。
- 性能优化不能破坏首屏可读性、缓存、样式或必要交互。
- Core Web Vitals 以 Search Console 的真实用户数据为准，PageSpeed 只用于复测和定位。
- Core Web Vitals 的良好目标为 LCP 不高于 2.5 秒、INP 不高于 200 毫秒、CLS 低于 0.1；这些是页面体验目标，不是保证排名的分数任务。
- 移动端与桌面端必须提供等价的主要正文、title、description、结构化数据、图片 alt 和可操作入口，并检查横向溢出、遮挡与文本孤行。
- 禁止为了消灭所有审计提示而进行没有用户价值的改动。

## 12. 发布前质量门槛

### 12.1 内容检查

- [ ] 一个主要搜索意图、一个主词、2 至 4 个辅助词已写入关键词池。
- [ ] 页面类型、目标读者、读者任务和下一步入口明确。
- [ ] 标题、H1、首段和 description 直接回答主要问题。
- [ ] 产品声明已按当前版本验证。
- [ ] 外部事实使用第一手或权威来源。
- [ ] 包含适用、不适用、限制、失败方式和人工确认点。
- [ ] 包含真实步骤或“输入 - 执行 - 输出”案例。
- [ ] 至少三个不同责任的内部链接有效。
- [ ] 中英文事实一致，表达不是机械翻译。
- [ ] 没有排名、流量、AI 引用或未发布能力承诺。

### 12.2 技术检查

- [ ] 页面返回成功状态且允许预期的索引行为。
- [ ] title、description、唯一 H1 和标题层级正确。
- [ ] canonical、hreflang、sitemap 和站内 URL 一致。
- [ ] JSON-LD 与页面可见内容一致。
- [ ] 页面锚点、内部链接、图片和资源无 404。
- [ ] 发布时间、更新时间、作者和适用版本正确。
- [ ] `llms.txt`、导航和相关文档已按页面重要性更新。
- [ ] 中文、英文、移动端和桌面端完成检查。

### 12.3 仓库验证

发布前必须运行仓库现有验证链：

1. `npm run validate:docs`，检查 Docs 与 Blog 的中英文文件、结构、front matter、图片和内部约束；
2. `npm run typecheck`；
3. `npm run build`；
4. `npm run validate:site`，逐个检查全部生成 HTML 的索引状态、title、description、H1、canonical、hreflang、JSON-LD、语言、图片、锚点、内部链接与 sitemap；
5. 使用本地浏览器检查中文、英文、移动端和桌面端的代表性页面模板、资源加载、横向溢出和控制台错误；
6. 对生产环境抽查 HTTP 状态、robots、sitemap、404 和部署后的语言正文；
7. `git diff --check`。

验证记录必须写明构建页数、可索引页数、`noindex` 页数、sitemap URL 数、内容源覆盖数、无法取得的数据和工具误报。PageSpeed 或 Search Console 无数据时必须写“未取得”，不得用实验室数据冒充真实用户指标。

Screaming Frog 可以用于补充全站爬取；未安装时，可以使用结构化 HTML 爬虫完成相同检查，但必须记录工具和检查范围。

## 13. 外部分发与权威信号

- 官网 Blog、Insights 或场景指南必须保留完整原文和规范 URL。
- GitHub Release、Discussions、V2EX、掘金、知乎、X 和合作渠道应当发布适合各平台的摘要、案例或讨论点，并链接回原文。
- 禁止在多个平台机械复制全文。
- 应当通过真实用户案例、集成项目、合作伙伴、部署报告、性能测试和故障复盘获得自然引用。
- 禁止购买外链、批量提交低质量目录、制造无业务关系互链或发布搜索垃圾内容。

## 14. 搜索与生成式引用复盘协议

### 14.1 基线

- 必须确认站点所有权，并提交中文与英文 sitemap。
- 每两周导出最近 28 天，并与前 28 天比较查询和页面。
- 必须区分品牌词与非品牌词，避免品牌展示掩盖内容增长。
- 必须记录新页面从发布到首次收录、首次展示和首次点击的时间。
- Search Console 负责查询、展示、点击、CTR、排名和索引信号；点击后的阅读或下一步行为必须来自站点分析、转化记录或明确用户反馈，不能由 Search Console 推测。
- Google AI Overview 与 AI Mode 的站点表现只使用 Search Console 当前提供的正式口径。2026-08-01 时相关点击、展示和排名计入 Web 搜索类型总量，尚无独立过滤器；不得把汇总流量反推成 AI 功能流量，也不能用第三方“AI 可见度分数”替代。
- Gemini Apps 表现使用固定问题复测、实际显示的来源 URL、来源准确性和站点分析中可观察的转介交叉验证。
- ChatGPT 表现使用固定问题复测、实际引用 URL、`utm_source=chatgpt.com` 转介和站点转化记录交叉验证。
- 订单或转化只能按明确的来源、落地页和归因口径记录；禁止仅因页面修改后短期订单增长就声称 GEO 带来该结果。

### 14.2 发布后 2 至 4 周

按页面和查询复盘，并执行：

| 信号 | 动作 |
| --- | --- |
| 有展示、低点击 | 检查标题、description、首段直接答案和摘要是否匹配意图。 |
| 站点分析或用户反馈显示有点击、下一步行为弱 | 补充案例、截图、边界、操作入口和相关内容。 |
| 平均排名 5 至 20 | 视为提升机会；其中 8 至 20 优先补充独特证据、相关主题和内部链接。 |
| 没有展示 | 先检查收录、canonical、意图匹配、竞争强度和外部引用。 |
| 近义查询落到多个页面 | 合并或明确页面责任，避免关键词蚕食。 |
| 查询与产品不匹配 | 降为观察或排除，不为流量扩大产品承诺。 |

禁止因短期没有展示就立即创建近义页面。每次复盘必须更新关键词池状态和维护记录。

## 15. 衡量指标

SEO/GEO 工作使用以下可验证指标，不使用“AI 可见度分数”替代真实结果：

- sitemap 覆盖率与已收录 URL 数；
- 非品牌查询的展示量、点击量和查询数量；
- 获得展示和点击的内容页数量；
- 核心查询对应页的 CTR 和排名趋势；
- 新页面首次收录、展示和点击时间；
- 来自 GitHub、合作伙伴和自然引用页面的有效访问；
- 内容带来的安装页、使用手册和产品介绍页访问；
- 移动端和桌面端真实 Core Web Vitals；
- 页面被搜索或生成式系统引用时，引用内容是否准确、是否仍符合当前版本；
- 来自 `utm_source=chatgpt.com` 的有效访问、落地页和按既定口径归因的转化。

## 16. 禁止事项

以下做法一律禁止：

- 堆叠关键词、`meta keywords`、隐藏文本或面向机器的重复答案；
- 批量生成泛化 AI 新闻、自动摘要、薄内容或仅换关键词的页面；
- 为查询变体或查询扇出批量创建近义页面，或用生成式 AI 规模化生产没有新增价值的内容；
- 购买外链、目录站群、无关互链或其他操纵排名行为；
- 为字数、H2/H3、表格、FAQ、图片或视频数量设定脱离意图的硬指标；
- 伪造 KD、搜索量、DA、DR、流量、用户案例、测试数据、来源或引用；
- 把推测、路线图、工具输出或竞品表述写成 xAgent 当前事实；
- 使用不受支持的 AI 专用 Schema，或让结构化数据超出可见正文；
- 机械复制中英文或外部平台全文；
- 无实质更新却修改日期或 sitemap `lastmod`；
- 为追逐流量创建与产品定位不符的“最佳”“免费”“完全自主”等页面；
- 承诺搜索排名、Featured Snippet、AI Overview、模型引用、流量或转化结果；
- 声称生成式系统存在固定 3 至 5 个推荐位、稳定推荐池或可持续名次；
- 把单次 Gemini 或 ChatGPT 回答当作排名结果，或忽略产品模式、地区、时间和上下文差异；
- 让生成式系统解释自身推荐原因，并把回答当作内部检索、排序或选择机制的证据；
- 按竞品段落顺序仿写页面，并将其表述为“AI 喜欢的信息排列”；
- 为迎合生成式系统刻意把正文切成碎片、重写成所谓“AI 文风”或追求虚假品牌提及；
- 把 `llms.txt`、特殊 AI 文本文件或自定义 GEO 标记描述为 Google 抓取、排名或 AI 引用要求；
- 使用自动化程序向 Google 搜索发送批量查询以检查排名；
- 为获得模型引用批量添加 FAQ 或 `FAQPage` Schema；
- 用页面上线前后的短期相关性代替流量、转介和订单归因证据。

## 17. 协议维护

- 新规则必须来自官方规范、当前仓库实现、真实 SERP、Search Console、用户反馈或可复核实验。
- 基于样本观察形成的规则必须记录查询、日期、样本和限制。
- 工具界面、排名、搜索量和结果页会变化，日期研究记录不得被改写成长期事实。
- 更新本协议时必须说明新增、修改或废止的规则及依据。
- 例外必须记录页面、原因、期限和复查条件，不能默认为全站规则。
